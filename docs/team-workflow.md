# 在场：两个人怎么一起开发

你们共用一个 monorepo，长期只维护 main。朋友主导前端设计，你负责全栈和发布；分工是减少撞文件，不是限制谁能写哪段代码。

## 分工

| 范围 | 主负责人 | 约定 |
| --- | --- | --- |
| Figma、视觉、组件样式、响应式和交互状态 | g2561845325-debug | 可以改页面 UI；不自行替换 API、认证或评分规则 |
| API、数据库、迁移、评分和研报算法、缓存、权限、发布 | wanghaha-GGbond | 改接口先说明契约；不顺手重做朋友正在改的视觉 |
| 页面容器、全局样式、导航、共享组件 | 任务开始时指定一人 | 另一人通过子组件或下一项任务接入，避免同改一个大文件 |

朋友写前端，你写后端时，先约定请求参数、返回类型、错误状态、空态和待审核状态。没有后端的设计可以在隔离 Preview 展示，但必须标成演示，不能在正式站模拟提交成功。

## 一项任务走一遍这个流程

1. 在 GitHub Issue 或 PR 开头写：做什么、谁做、会改哪些路径、接口是否变化。开始前看一下对方的开放 PR。
2. 各自在自己的 clone/worktree 工作，从最新 origin/main 建短分支，如 feat/ui-company-filter、feat/api-company-stats。不要共用一个工作目录同时切分支。
3. 尽早开 Draft PR；设计任务附 Figma 链接、桌面/手机截图和状态清单。一个 PR 保持一个主题。
4. 后端使用真实接口，前端消费既有契约。共享类型变化跑 Web/iOS 两端检查；数据库迁移必须向前兼容，并在隔离库验证。
5. 提交合并前更新 origin/main，将 main 合入自己的分支后重新跑检查。不要从已关闭 PR 或旧 release 继续堆叠开发。
6. 所有适用 CI、数据库和 Preview 检查通过后正常 merge，**不需要等另一人点 Approve**。不直接 push main，不跳过失败检查。
7. 合并后删除任务分支，下一项从新的 main 开始。Preview 是测试环境，不是两个人长期共同堆代码的 test 分支。
8. 正式发布由 wanghaha-GGbond 负责：从 main 已包含的提交构建，记录源码/平台版本、迁移、验收及回退点。merge 不等于已部署。

## 避免冲突的四条硬规则

- 全局样式、导航、lockfile、迁移 journal 同一时间只由一项任务修改；必要时先在 PR 留言协调。
- 数据请求和业务状态留在容器/查询层，展示组件接收 props；不要为换 UI 复制一套 API 客户端或评分公式。
- 冲突不能整文件选 ours/theirs。视觉由设计负责人判断，数据和权限由全栈负责人判断，然后重跑测试。
- 小步提交、短分支；不要把旧分支完整覆盖 main，也不要把两个 PR 打成一个无法单独回退的大包。

没有方法能保证永远零冲突。这些规则让冲突更少、范围更小，而且能在发布前被发现。

## 两个 agent 都照这个做

先读 AGENTS.md、CONTRIBUTING.md 和本页，检查工作区与开放 PR。保留已有改动；先声明任务路径和接口边界。只提交自己负责的内容；不强推、不重置对方代码、不改审批保护、不带入密钥。PR 写清测试结果、真实/演示状态和没有完成的部分，不把“CI 通过”说成“正式站已经更新”。

## Figma 是共同设计源

使用「在场 Web · 原型与交互」文件：线上基线、组件规范、下一版交互分别维护。页面或组件注明对应版本、状态和代码路径；实现完成后补 Preview 链接。视觉定稿采用可编辑 Design 图层，不以整页截图冒充可编辑原型。没有写入连接时明确记录未同步，不宣称已固化。
